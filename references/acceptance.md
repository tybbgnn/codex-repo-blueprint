## 五维验收

1. **本层节点是否准确概括其工作？** 不看 BB，能否知道它做什么、什么情况下执行、产生什么结果？有没有把只进入共有尾部的节点说成执行了完整动作？
2. **同层节点能否直接读成流程？** 能否看清先后、分支、汇合、循环和提前结束？如果必须靠隐藏 BB 端口才能消除误解，判上层不合格。
3. **展开是否增加有用信息？** 上层职责能否由下层步骤解释清楚？哪些层给人读，哪些只是核验结构，要区分。
4. **重要流程是否在到达 BB 前已经讲清？** 关键业务动作、决策、循环、外部协作、异常结果，应在语义层可理解。
5. **事实依据是否充分？** 从上往下：每个节点的名称、成员、顺序、条件是否有 Rust / MIR / BB 路径支持（只挂一组 BB 不算依据）。从下往上：下层的工作和重要分支是否被上层准确概括，有没有遗漏、提前宣告结果。

任何一维不合格，回到阶段 2 修改，再重新验收。

## A48 教训

反面教材：先选 loop / exit / commonAfter 展示模板，再把静态列表前缀填成 members，导致条件后继被误当整个循环的出口，且同一 action 同时出现在 members 和 commonAfter 中。根因是没有独立证明区域成员与新增角色的语义等价。

正确做法：每层只从下一层真实关系推导；每个 control / readingScope 记录组合依据；不用静态区间前缀定义循环成员；不凭节点名猜角色。

## 5 条回归断言

1. `stop-finish` 不能仅凭该记录转换成整个循环的 `exit`。
2. scope 外部后继（含 commonAfter）不得同时属于 scope 内部成员。
3. 循环成员须有关系依据，不以静态区间前缀为唯一依据。
4. 恢复回到 input 必须保持原 `arrival`/`suffix`，不插入无依据节点、不复制 tail。
5. 每个新增语义角色有来源或明确可核对的组合推导。

## 阶段 7 原则检查

运行：

```bash
python3 scripts/check_principles.py --out "$OUT" --report "$OUT/stage7/principles.json"
```

报告逐项给出 `pass/fail/review`、数字证据和定位。退出码 1 表示机器失败，2 表示输入错误，0 仅表示已执行机器项无失败，不代表待审查项通过。

| 原则 | 机械检查要点 | 必须审查 |
|---|---|---|
| P1 | 阅读节点类型、BB 引用、facts 全覆盖 | 职责、边界、源码/路径依据成立 |
| P2 | phase_order/源阅读树与输出顺序一致 | 真实执行顺序，不只是数组同序 |
| P3 | 技术事件未升级，execution evidence 可解析 | 下层方向/条件支撑上层概括 |
| P4 | 原边 ID 唯一，members/clauses 可对应 | 逐子句核对条件、过程、结果 |
| P5 | 无 EX/RET/共享 cleanup/return 展示容器 | 真实业务出口的结果注释 |
| P6 | 端点祖先闭包、body 身份、消息配对 | 目的组与真实端点身份 |
| P7 | 展示字段无明确技术噪声 | 八类噪声清除且未误删业务语义 |
| P8 | local_mechanism 未成独立 actor | 机制对象的业务地位与折入位置 |
| P9 | invocation/request/return/binding/端点唯一配对 | 成员规范键和跨层引用 |
| P10 | decision 值覆盖、control/scope、摘要、对账表 | 可见表达准确且无头尾清单 |
| P11 | loop 入口/出口、commonAfter、回边 | break/continue/return 与源码一致 |
| P12 | goal BB 集合等于子 action 并集 | 真实入口/出口和业务循环边界 |
| P13 | goal/action 中文标签，body 原名 | 措辞准确、源码术语完整 |
| P14 | 详情覆盖 prelude+goals+actions，范围界内 | 默认源码可滚到底，选择高亮正确 |

G1–G11 与 P 检查同跑，不用旧案例数量判定通过。`fail` 或未关闭的 `review` 均不能宣称验收完成。BB组应描述自己的操作，不能机械复制父 action 的完整职责。
